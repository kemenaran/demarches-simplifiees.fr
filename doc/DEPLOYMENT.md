# Deployment documentation

This is the documentation for deploying and upgrading a production instance of demarches-simplifiees.fr.

## 1. Pre-requisites

demarches-simplifiees.fr is a standard Rails app, and can be deployed using standard methods (PaaS, Docker, bare-metal, etc.)

It requires several external services and dependencies to run. These dependencies can be provided all on the same host, or on different hosts or machines.

### Services

- **PostgreSQL** (version >= 15)

	Postgres is used as the database for all application data. Only a single instance and a single database is required (there is no sharding as of now).
- **An email provider**

	Emails are sent for enrolement, account management, notifications, etc.
 The application can use either:
	- An `smtp` email service,
	- A properly-configured `sendmail`,
	- A [Brevo](https://www.brevo.com) account.
	
	> [!TIP]
	> Email reception is critical for the users.
	>
	> We strongly recommand a well-configured email server with SPF, DKIM and DMARC, an IP address with a good reputation, a dedicated IP if possible, and closely monitoring email errors.
- **An Object Storage**

	The Object Storage is used to store files:
	
	- sent by the users (like supporting documents),
	- sent by the admins (like procedure notices),
	- generated by the application (like attestations).
	
	Files can be stored to either:
	
	- an Amazon `S3` (or any S3-compatible) Object Storage,
	- an `OpenStack` Object Storage,
	- the local filesystem of the application (not recommended in production).
	
	As this storage will contain <abbr title="Personnally Identifiable Informations">PII</abbr>, it should be well secured (and at least encrypted at rest).
- **`weasyprint_server`**

	WeasyPrint is a locally-running tool used to convert HTML attestations to PDF. [weasyprint_server](https://github.com/demarches-simplifiees/weasyprint_server) is a small Python shim around WeasyPrint to expose a network API.
- **(Optional) Redis**

	Redis may be used as an application-wide cache, and as the backend for asynchronous job processing.
	
	See the "Running the asynchronous jobs" section below for choosing a async jobs backend, and determining if you need Redis or not.
	
- **(Optional) `ds_proxy`**

	[ds_proxy](https://github.com/demarches-simplifiees/ds_proxy) encrypts file transferts between the Object Storage and the application.
	
	Set it up if at-rest encryption of the files does not meet your security requirements, and you need to add an extra layer of security by encrypting the content of the files themselves during transfert and storage.

- **(Optional) Matomo**

	Matomo can be used to track usage statistics.

### API Keys

-  **"API Entreprise" API Key**

	[API Entreprise](https://entreprise.api.gouv.fr/) is used to retrieve a wide range of company data from a SIRET code.
	
	Use the API Entreprise website to [submit a request](https://entreprise.api.gouv.fr/) and obtain an API key.
- **(Optional) Signaturit/Universign API Key**

	[Signaturit](https://www.signaturit.com) (formerly Universign) can be used to sign timestamped audit logs of the application activity, for compliance purpose.

## 2. Preparing the server

The web application and the asynchronous jobs require some binary dependencies.

- **Ruby**

	[Ruby](https://www.ruby-lang.org) runs the main application code. Use the [ruby version specified in the repository](https://github.com/kemenaran/demarches-simplifiees.fr/blob/main/.ruby-version).

	> [!NOTE]
	> [`rbenv`](https://github.com/rbenv/rbenv) is the preferred way to install ruby and manage ruby versions; but any method of installing Ruby will do.
	
	> [!TIP]
	> For better performances, build Ruby with `jemalloc` (requires `libjemalloc` to be present) and `yjit` (requires `rustc` to be present).
  >
  > ```shell
  > rbenv install 3.4.4 -- --with-jemalloc --enable-yjit
  > ```
- **Bun**

	[Bun](https://bun.sh/) is the Javascript execution environment that compiles and packages the assets. It is required to pre-build the assets before starting the application.
	
	Once the assets are built, bun is not used at runtime.
	
	> [!TIP]
	> See https://bun.sh/docs/installation for setup instructions.
- **Imagemagick**

	`imagemagick` (compiled with `gsfonts` support) is used to generate image thumbnails and watermark identity documents.
	
	> [!WARNING]
	> Remember to restrict ImageMagick's policy to block exploitation of malicious images:
	> the default configuration is usually insufficient for images from the web.
	>
	> For example, on Debian/Ubuntu in `/etc/ImageMagick-6/policy.xml`:
	>
	> ```xml
	> <!-- in addition to the default policy, add at the end of the file -->
	> <policymap>
	>     <policy domain="coder" rights="none" pattern="*"/>
	>     <policy domain="coder" rights="read | write" pattern="{JPG,JPEG,PNG,JSON}"/>
	>     <policy domain="module" rights="none" pattern="{MSL,MVG,PS,SVG,URL,XPS}"/>
	> </policymap>
	> ```
- **(Optional) ClamAV antivirus**

	[ClamAV](https://www.clamav.net/) can be used to scan attachments sent by the users for known viruses.

## 3. Deploying demarches-simplifiees.fr

### 3.1 Copying the code

Use `git` to download the release you want to deploy:

```shell
git clone --depth 1 https://github.com/demarches-simplifiees/demarches-simplifiees.fr && cd demarches-simplifiees.fr
git checkout <release_tag>
```

> [!NOTE]
> If you prefer to use a tarball, source archives are available from the [Releases page](https://github.com/demarches-simplifiees/demarches-simplifiees.fr/releases/).

### 3.2 Installing dependencies

Install the required Ruby and Javascript dependencies with:

```shell
bundle install
bun install
```

### 3.3 Configuring with env vars

The application uses environment variables for its configuration. Browse the configuration files to discover mandatory and optional settings, and set up an environment with the proper variables declared.

Files of interest:

- [`config/database.yml`](https://github.com/demarches-simplifiees/demarches-simplifiees.fr/blob/main/config/database.yml): contains the env vars to use for connecting to the database.
- [`config/env.example`](https://github.com/demarches-simplifiees/demarches-simplifiees.fr/blob/main/config/env.example): contains the mandatory env vars that **must** be present for the application to start.
- [`config/env.example.optional`](https://github.com/demarches-simplifiees/demarches-simplifiees.fr/blob/main/config/env.example.optional): contains the optional env vars that may be used to fine-tune the application.

> [!NOTE]
> Don't forget to define `RAILS_ENV=production`.

> [!WARNING]
> Ensure that all these environment variables (including `RAILS_ENV`) are defined before running any `rails` command.

### 3.4 Setting up the database

Once the database connection is properly configured (see `config/database.yml`), create the schema using:

```shell
rails db:prepare
```

### 3.5 Compiling the assets

Before starting the application server, assets must be compiled and bundled:

```shell
rails:assets_precompile
```

### 3.6 Running the server

Start puma (the application web server) using:

```shell
rails server -p 8080
```

> [!NOTE]
> It is recommanded to use a dedicated web server (like `nginx` or `apache`) as a proxy between the internet and the application.
> 
> In that case, the dedicated web server must also be configured to serve static files in the `/public` directory.
> 
> (If you prefer exposing `puma` directly to the internet, define the `RAILS_SERVE_STATIC_FILES` environment variable, and Rails will serve static files itself, at the cost of some performance.)

### 3.7 Running the asynchronous jobs

Two async job backends are available:

- [delayed_job](https://github.com/collectiveidea/delayed_job): simple, no dependencies.
- [sidekiq](https://github.com/sidekiq/sidekiq) (default): performant, error-resilient – but requires Redis.

Choose your job backend using the `RAILS_QUEUE_ADAPTER` environment variable:
 
```shell
RAILS_QUEUE_ADAPTER=delayed_job  # Use delayed_job
RAILS_QUEUE_ADAPTER=sidekiq      # Use sidekiq
```

The command to start the jobs server depends on your async jobs backend:

**For `delayed_jobs`:**

```
rails job:work
```

**For `sidekiq`:**

```
bundle exec sidekiq
```

### 3.8 Scheduling recurrent tasks

Recurrent tasks are run using asynchronous jobs, scheduled at regular interval.

To set them up, run:

```shell
rails jobs:schedule
```

This only need to be performed once.

### 3.9 Customizing text and images

See [Customization.md](customization.md).

## 4. Upgrading to a new release

Upgrades are engineered not to require any downtime.

Usually, an upgrade deployment goes like this (in pseudo-code):

```
# Run database schema migrations (e.g. `bin/rails db:migrate`)
# For each server:
  # Stop the server
  # Get the new code (e.g. `git clone git@github.com:betagouv/demarches-simplifiees.fr.git`)
  # Install new dependencies (e.g. `bundle install && bun install`)
  # Restart the app server
# Run data migrations (e.g. `rake after_party:run`)
```

On the main instance, this deployment flow is implemented using [`mina`](https://github.com/mina-deploy/mina), which automatically sshs to the application servers, run the appropriate commands (see `lib/tasks/deploy.rake` and `config/deploy.rb`), and restarts the puma webserver in a way that ensures zero-downtime deployments.
A deploy on multiple application servers is typically done using:
```shell
DOMAINS="web1 web2" BRANCH="main" bin/rake deploy
```

### 4.1 Standard upgrade path

Theoretically, only deploying each version sequentially is fully supported. This means that to deploy the version N+3, the upgrade plan should be to deploy the version N+1, N+2 and then only N+3, in that order.

Release notes for each version are available on [GitHub's Releases page](https://github.com/betagouv/demarches-simplifiees.fr/releases). Since 2022, when a release includes a database schema or data migration is present, this is mentionned in the release notes.

### 4.2 Upgrading several releases at once

Upgrading from several releases at once (like migrating directly from a version N to a version N+3) is theoretically unsupported. This is because database schema migrations and data migrations have to run in the exact order they were created, along the application code as it was when the migration was written.
That said, it is possible to batch the upgrade of several releases at once, _provided that the data migrations run in the correct order_.

The rule of thumb is that _an intermediary upgrade should be done before every database schema migration that follows a data migration_.

_NB: There are some plans to improve this, and contributions are welcome. See https://github.com/betagouv/demarches-simplifiees.fr/issues/6970_
